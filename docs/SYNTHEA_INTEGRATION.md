## 1. Overview & Architectural Principles

The Synthea integration in AI Virtual Hospital provides an isolated, reliable, and safe pipeline for generating, inspecting, and simulating synthetic patient journeys using **FHIR R4 (Fast Healthcare Interoperability Resources Release 4)**.

### Core Architectural Safeguards

1. **No External Network Dependencies (SyntheticMass Retired)**:
   The external MITRE SyntheticMass service (`https://synthea.mitre.org/fhir-api`) is officially retired. AI-VH strictly avoids external API dependencies for synthetic patient data. All generation and ingestion occur through self-hosted local execution or bundled offline datasets.
2. **Strict Service Layer Isolation**:
   The frontend web application never interacts directly with generator binaries, external FHIR servers, or filesystem directories. It communicates exclusively through internal, authenticated backend endpoints under `/api/demo-patients/*`.
3. **Comprehensive Multi-Resource FHIR R4 Adapter**:
   A dedicated adapter maps complex Synthea transaction bundles into normalized clinical domain entities and a unified chronological timeline across 9 core FHIR resource categories.
4. **Zero-Dependency Offline Fallback**:
   A curated set of 5 diverse, high-fidelity synthetic patient records is bundled directly in the repository (`data/synthea/demo_patients/`), ensuring that developers and reviewers can immediately inspect realistic clinical timelines with zero initial setup.
5. **Hospital Admission Bridge**:
   Synthetic demo patients can be dynamically admitted into Metropolitan General's live database repository (`/api/demo-patients/:id/admit`), enabling immediate handoff to clinical agents, triage, and 3D ward simulation.

## 2. FHIR R4 Adapter & Unified Timeline Model

Synthea produces standard FHIR R4 JSON Transaction Bundles. The internal adapter (`src/vh/synthea/fhir_adapter.py`) parses and extracts data across all major clinical resources:

| FHIR R4 Resource | Standard Ontologies | Internal Field Mapping |
| :--- | :--- | :--- |
| **Patient** | Identifier, Name, Address, Telecom | Demographics, MRN, Age, Sex, Contact |
| **Encounter** | SNOMED-CT, HL7 ActCode (IMP, EMER, AMB) | Inpatient/Emergency visits, Provider, Reason |
| **Condition** | SNOMED-CT, ICD-10 | Active and past diagnoses, Onset timestamp |
| **Observation (Vitals)** | LOINC (Heart rate, Blood pressure, SpO2, Temp) | Baseline and telemetry vital sign panels |
| **Observation (Labs)** | LOINC (Troponin, Leukocytes, Glucose, Creatinine, eGFR) | Structured lab investigations, Values, Units |
| **MedicationRequest** | RxNorm | Prescriptions, Dosages, Routes, Instructions |
| **AllergyIntolerance** | SNOMED-CT | Substance, Criticality (high/low), Clinical status |
| **Procedure** | SNOMED-CT | Interventions, Surgical/Diagnostic procedures, Timestamps |
| **Immunization** | CDC CVX | Vaccine history, Administration dates |
| **CarePlan** | SNOMED-CT | Clinical management pathways, Goals, Activities |

### Unified Chronological Timeline

The adapter collates all 9 resource categories into a normalized, reverse-chronological sequence (`GET /api/demo-patients/:id/timeline`). Each timeline event includes:
- `id`: Resource identifier
- `resource_type`: FHIR resource type
- `category`: Classification lane (encounter, condition, observation, medication, allergy, procedure, immunization, careplan)
- `timestamp`: ISO 8601 sortable timestamp
- `display_date`: Human-readable date string
- `title` & `subtitle`: Clear clinical narrative descriptions
- `code` & `system`: Standardized terminology (LOINC, SNOMED, RxNorm, CVX)
- `details`: Resource-specific structured values (e.g., blood pressure components, medication dosage instructions, lab normal units)

## 4. Self-Hosted Execution Guide

AI-VH supports three operational modes for synthetic patient generation:

### Option A: Bundled Zero-Dependency Fallback (Default)
- Zero external runtime required (runs on pure Python 3.13 standard libraries).
- Uses the verified deterministic generator engine in `src/vh/synthea/generator.py` and pre-built bundles in `data/synthea/demo_patients/`.
- Provides instant sub-millisecond response for UI testing, development, and unit test suites.

### Option B: Docker Container Execution
The repository includes a dedicated Synthea container definition in `docker/synthea/Dockerfile` pinned to official release `v3.3.0`.

To build the Synthea container locally:
```bash
docker build -t ai-vh-synthea:latest -f docker/synthea/Dockerfile .
```

To run an on-demand population generation with Docker:
```bash
docker run --rm -v "${PWD}/data/synthea/output:/output" ai-vh-synthea:latest -p 10 -s 42 Massachusetts
```

Using Docker Compose:
```bash
docker compose run --rm synthea -p 5 Massachusetts
```

### Option C: Standalone Local Java JAR
If Java 21+ JRE is installed on the host system:
1. Download official Synthea release:
   ```bash
   curl -L -o docker/synthea/synthea-with-dependencies.jar https://github.com/synthetichealth/synthea/releases/download/v3.3.0/synthea-with-dependencies.jar
   ```
2. Run generation:
   ```bash
   java -jar docker/synthea/synthea-with-dependencies.jar --config docker/synthea/synthea.properties -d ./data/synthea/output -p 5 Massachusetts
   ```

## 5. REST API Contract

All synthetic patient endpoints are mounted under `/api/demo-patients`:

### 1. List Demo Patients
- **Endpoint**: `GET /api/demo-patients`
- **Response**:
  ```json
  {
    "disclaimer": "SYNTHETIC DEMO DATA ONLY...",
    "total": 5,
    "patients": [
      {
        "id": "pat-demo-001",
        "mrn": "SYNTH-DEMO-001",
        "name": "Robert Thomas Miller",
        "gender": "male",
        "birth_date": "1964-04-12",
        "age": 62,
        "city": "Boston",
        "state": "Massachusetts",
        "active_condition_count": 2,
        "encounter_count": 1,
        "observation_count": 4,
        "medication_count": 2,
        "allergy_count": 1,
        "procedure_count": 1,
        "immunization_count": 1,
        "care_plan_count": 1,
        "primary_diagnoses": ["Myocardial infarction", "Hypertension"]
      }
    ]
  }
  ```

### 2. Get Patient Medical Profile
- **Endpoint**: `GET /api/demo-patients/{patient_id}`
- **Response**: Full structured record containing demographics, active conditions, encounters, medications, allergies, vitals, labs, procedures, immunizations, and care plans.

### 3. Get Unified Clinical Timeline
- **Endpoint**: `GET /api/demo-patients/{patient_id}/timeline`
- **Response**: Reverse-chronological array of clinical events with human-readable titles, timestamps, and ontological coding.

### 4. Get Raw FHIR R4 Bundle
- **Endpoint**: `GET /api/demo-patients/{patient_id}/raw`
- **Response**: Unmodified FHIR R4 JSON Transaction Bundle.

### 5. Generate Synthetic Population
- **Endpoint**: `POST /api/demo-patients/generate`
- **Payload**:
  ```json
  {
    "population": 5,
    "seed": 42,
    "state": "Massachusetts",
    "gender": "M",
    "age_range": [30, 65]
  }
  ```
- **Response**: Generation execution metadata, generated patient IDs, and summary cards.

### 6. Hospital Admission Bridge
- **Endpoint**: `POST /api/demo-patients/{patient_id}/admit`
- **Description**: Translates the synthetic patient profile into an admitted inpatient record in Metropolitan General's database with assigned bed and acuity.

## 6. Population Bias & Saudi Healthcare Localization

Synthea was originally developed in the United States and defaults to US Census demographic tables (such as Massachusetts state distributions), US epidemiological models, and US healthcare billing practices. When deploying or evaluating clinical AI agents in Saudi Arabian healthcare contexts, the following key differences must be accounted for:

### 1. Epidemiological & Disease Prevalence Discrepancies
- **Type 2 Diabetes Mellitus & Metabolic Syndrome**:
  Saudi Arabia has an adult diabetes prevalence estimated between 18% and 24% (among the highest globally), compared to approximately 10% to 12% in standard Synthea US distributions. Furthermore, diabetic onset occurs at significantly younger median ages in the Gulf region, with higher rates of early diabetic nephropathy and retinopathy.
- **Hemoglobinopathies & Genetic Conditions**:
  Inherited red blood cell disorders, particularly Sickle Cell Disease and Beta-Thalassemia, are prevalent in specific Saudi provinces (e.g., Eastern Province and southwestern regions such as Jazan). National premarital screening programs explicitly track these conditions. Standard Synthea population generators completely omit regional hemoglobinopathy prevalence unless custom modules are supplied.
- **Infectious Disease Spectra**:
  Synthea standard modules frequently simulate tick-borne Lyme disease and Rocky Mountain spotted fever, which are virtually non-existent in the Arabian Peninsula. Conversely, Saudi clinical protocols must actively monitor for Middle East Respiratory Syndrome Coronavirus (MERS-CoV), regional cutaneous leishmaniasis, Dengue fever (in western coastal cities), and unique multi-pathogen respiratory patterns associated with Hajj and Umrah mass-gathering events.
- **Cardiovascular Age of Onset**:
  Acute coronary syndromes frequently present in Saudi male cohorts in their late 30s and 40s due to clustered metabolic risk factors, high smoking prevalence, and physical inactivity.

### 2. Administrative, Demographic & Cultural Discrepancies
- **Dual Calendar Systems (Hijri vs Gregorian)**:
  Official medical records in the Kingdom of Saudi Arabia frequently index patient birth dates and historical health events using the Umm al-Qura Hijri calendar (AH) alongside the Gregorian calendar (CE). Synthea generates Gregorian timestamps exclusively.
- **Quadripartite Naming Traditions**:
  Saudi patient identification utilizes Arabic quadripartite naming conventions (Given Name - Father's Name - Grandfather's Name - Family/Tribe Name, e.g., *Mohammed bin Abdullah bin Saleh Al-Ghamdi*), differing markedly from Western Anglo-Saxon First/Last name distributions.
- **National Identifier Systems**:
  SyntheticMass and Synthea assign US Social Security Numbers (SSN) and US ZIP codes. The Saudi national healthcare architecture utilizes the 10-digit Saudi National ID (starting with 1 for Saudi citizens, 2 for resident expatriates with Iqama) and the National Address short code system.
- **Pharmaceutical Formulary & Regulatory Coding**:
  Synthea maps medications using US National Library of Medicine RxNorm concepts. While clinically compatible, Saudi hospitals operate under Saudi Food and Drug Authority (SFDA) drug codes and national formulary availability (e.g., specific antimicrobial restrictions and insulin brand distributions).
